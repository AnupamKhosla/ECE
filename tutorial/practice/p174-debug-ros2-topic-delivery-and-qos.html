Build the diagnosis around matched endpoints

A publisher offers a QoS profile. A subscriber requests a profile. A best-effort offer can satisfy a best-effort request. A reliable request needs a reliable offer. In discovery both endpoints can be listed under the same topic, while an incompatible pair exchanges no messages. Use endpoint properties, match count and the incompatible-policy event together. ROS 2 Jazzy QoS compatibility rules.

Durability determines what a late reader is eligible to receive. In this exercise a transient-local publisher retains a sample and a matching late reader receives it while that publisher remains alive. A volatile late reader sees only new publications. Deadline tests the interval between updates. Lifespan limits how long a published sample remains deliverable.

Run the local Jazzy exercise

Download check_qos.py. Use a separate Ubuntu 24.04 VM or an unused local ROS domain with Jazzy, rclpy and std_msgs. The script starts two temporary nodes in one Python process and publishes synthetic integers under /ece_qos_lab/. No navigation, camera or motor nodes are needed.

source /opt/ros/jazzy/setup.bash
export ROS_AUTOMATIC_DISCOVERY_RANGE=LOCALHOST
export ROS_DOMAIN_ID=74
RMW_IMPLEMENTATION=rmw_fastrtps_cpp python3 check_qos.py > fast-dds.csv

To repeat with Cyclone DDS, install its Jazzy middleware package. Keep the discovery scope local and use an unused domain. Each check stops with an error if evidence is missing or the result differs.

sudo apt install ros-jazzy-rmw-cyclonedds-cpp
RMW_IMPLEMENTATION=rmw_cyclonedds_cpp python3 check_qos.py > cyclone-dds.csv

Read the results by case and observation. Elapsed times use a local monotonic clock and mark when the check recorded each result. Download the observed Fast DDS run and observed Cyclone DDS run.

Explain the four outcomes

CaseCondition testedOutcome in both observed runs
ReliabilityBest-effort publisher. One reader requests reliable, one best effort.Graph discovers two readers, publisher matches one. The rejected reader reports RELIABILITY. The matched reader gets 10, 11 and 12.
DurabilityPublisher sends 40 before two subscribers join, then sends 41 after both match.The transient-local reader sees 40 before the new publication. The volatile reader first sees 41. Both get 41.
DeadlinePublisher offers 120 ms. Readers ask for 60 and 120 ms. Pause the publisher after three readings.The 60 ms request reports DEADLINE incompatibility. The 120 ms reader remains matched through three observed deadline misses and receives value 24 when publication resumes.
LifespanTransient-local publisher sets a 160 ms lifespan. Reader starts after more than 450 ms.The matched late reader receives no expired 301 value. It receives the new 302 value.

Deadline events tell you that expected updates did not arrive. They leave the endpoint connection in place. Lifespan starts from middleware publication, so a queued sensor sample may already be old before this limit begins. A robot still needs application checks for the acquisition timestamp, data quality and the expected map or mission generation.

Use the sequence on a failing subscriber

  1. On the isolated ROS domain, use ros2 topic info -v on the active topic in P141. Compare publisher and subscriber types, reliability and durability. If both endpoints exist, find which pair is actually matched.
  2. Change the durability reader in the fixture to volatile. Update the expected observation and explain why waiting longer cannot recover its old publication. Restore the original settings for the remaining cases.
  3. Before treating a fresh callback as reauthorization, verify the message belongs to the current operation. For a scan, inspect message stamp, clock and transform availability. For a retained configuration, require the current map or recipe revision.
