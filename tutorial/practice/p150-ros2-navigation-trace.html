P150

Find the first failing boundary in a ROS 2 navigation trace

A topic can keep publishing an old stamp. A valid transform for the latest frame can be too old for the scan. Reconstruct what the navigation stack could know at each sample.

Time 45–70 minutes offline, plus an optional Gazebo recordingBefore this P141 · T38

Keep arrival time, source time and transform time separate

A logger records when it receives each observation. A stamped sensor message represents when the producer says the observation happened. TF2 needs a suitable transform chain at that source time. For a chain with several dynamic edges, the common interval is the intersection of the edge histories. The newest transform on one edge can be too recent or too old relative to the history available on another. A static camera mount transform has different timing semantics. ROS 2 Jazzy · TF inspection tool.

At 30°/s yaw, a pose paired 120 ms late is rotated by 3.6°. A feature 2 m away can appear displaced sideways by about 126 mm. Confirm whether the observation time and transform time share the same clock before blaming calibration.

Work a trace without ROS installed

Download the navigation trace. The compact synthetic worksheet represents snapshots of a trace, with all times in milliseconds. Use a spreadsheet or subtract by hand. Each run has three rows. Only compare times within a single run.

ColumnsInterpretation
host_elapsed_ms, sim_clock_msHost monotonic time since case start and the most recently observed simulation clock. Use consecutive rows to detect a frozen simulation clock.
scan_stamp_msTime written in the most recent scan header. Compare it with simulation time and with the previous scan stamp.
tf_first_ms, tf_last_msEarliest and latest common lookup times across the required dynamic TF chain at the snapshot.
cmd_mps, odom_x_m, odom_stamp_msTraining velocity command, reported x position and odometry source time. The route is straight. A different run would also need yaw and lateral position.
  1. Calculate scan age as simulation clock minus scan stamp. A scan over 150 ms old exceeds this lesson’s training limit. A negative age calls for a clock or timestamp check. Calculate how far a valid scan falls outside the common TF interval.
  2. Compare the host clock and simulation clock across rows. Identify which row first proves loss of progress. Then check command and feedback only after time and geometry make sense.
  3. For each case, give the first failing boundary, one next observation that disambiguates the cause, and the values that would prove a recovery. Keep timing evidence from before and after the change.
Check the trace diagnoses

A. Healthy reference. Scan age is 70 ms and falls inside the TF history. Command stays at 0.18 m/s and estimated position progresses by 0.036 m each 200 ms.

B. By the second row TF ends 70 ms before the scan. Wait for suitable transform history or investigate the delayed publisher. Verify each dynamic edge at scan time.

C. The host progresses while simulation clock and source stamps stay unchanged. Check whether Gazebo is paused or the clock bridge stopped before adjusting the controller.

D. The scan stamp is far in the future relative to simulation time. Compare the sensor publisher clock and use_sim_time across the simulator and its consumers.

E. Scan and TF timing are healthy and odometry time advances, but estimated position stays fixed with a persistent nonzero command. Check the command subscriber, controller state, wheel feedback and independent motion before deciding between a drive and odometry fault.

F. Simulation time advances while the scan stamp stays at 47,930 ms. The scan is 270 ms old by the second row, although the transform interval includes it. Check new scans at the sensor publisher and bridge, then compare whether the consumer receives unique source stamps.

G. The second scan is 70 ms old, but requires a lookup 30 ms earlier than the first available transform. Check for a TF publisher restart or an incomplete buffer. In the third row the dynamic history covers the current scan again.

Compare with an observed simulator pause

Download the measured pause run. The data comes from a headless ROS 2 Jazzy and Gazebo Harmonic TurtleBot3 sandbox. A subscriber sampled the last received clock and scan stamp at approximately half-second intervals measured by the observer’s monotonic clock. These are snapshots of delivered values. Keep phase labels hidden for a first pass and find the longest interval over which both simulation timestamps stay fixed.

Check what the real pause evidence establishes

Between observer times 3.352 s and 5.852 s, at least 2.500 observable seconds elapsed with /clock at 280.149 s and the last scan stamped 280.002 s. A fixed difference of 147 ms alone gives no indication that the stream was frozen. The next sampled run state at 6.412 s contains a newer clock and scan stamp. This run had a deliberate Gazebo pause. For a new investigation, check simulator state and the clock bridge to distinguish the causes of a similar gap.

Record a comparable case in the isolated simulator

After completing P141, discover which topics your local simulation actually publishes and use their names below. In a new terminal in that same isolated simulation, record a normal run and a separate run with a short controlled pause in the simulator. Keep the two bags distinct and record the scenario in a note. Stop the recorder with Ctrl+C after the run. The recorder waits for the first simulation clock sample when given --use-sim-time.

ros2 bag record --use-sim-time -o nav_case --topics /clock /tf /tf_static /scan /odom /cmd_vel
ros2 bag info nav_case

Check topic types and message counts first. A topic may be listed with a count of zero if the robot never moved or the recorder did not receive it. Use the host time you observed or logged at pauses, because the bag’s recording time also follows simulation time in this configuration. Header timestamps are part of the message. Keep both when investigating timing. The example below replays only sensor, clock and transform topics in a separate isolated software session after the simulator closes.

ros2 bag play nav_case --topics /clock /tf /tf_static /scan /odom

Repeat the same observation with live playback topics. A compressed gap in simulated time may only be visible in the host notes. Save the run conditions, relevant message stamps, transform evidence and the first change after recovery. In one measured goal run, the MCAP recorded 178 scans, 990 odometry messages and 62 velocity messages. Compare message counts with actual run duration and topic behavior.
