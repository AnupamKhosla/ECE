P169

Check CAN data freshness through dropouts and restart

The CAN monitor can show steady bus traffic while the controller has no new valid wheel-speed sample. Send a fixed sequence through Linux virtual CAN and trace exactly which sample resets the freshness timer.

Time 45–65 minBefore this P49 · Decode a virtual CAN frame · T38 · Sampling, buses and evidence

Watch. Watch frames cross a local virtual CAN interface. Then measure receiver behavior when a sample arrives too late. The EV Engineer · Virtual CAN interface tutorial.

Define what can refresh the signal

This training wheel monitor expects a valid frame on standard ID 0x421 approximately every 100 ms. It becomes stale after 350 ms without an accepted sample, measured by the receiver’s monotonic clock. An explicit supervised generation change clears the previous evidence. The fictional format below uses little-endian fields and has no link to a vehicle or a production CAN protocol.

Payload bytesInterpretationUse in the receiver
0–1Unsigned generationOnly the generation armed by the test supervisor is accepted.
2Unsigned counter, modulo 256Advance 1–127 to accept. Zero is a duplicate. Larger steps are old or ambiguous.
3Quality enumerationOnly value 1 identifies a usable measurement.
4–5Signed wheel speed, 0.1 rpm per countDecode the sign before multiplying by the scale.
6–7Source sample tick, 1 ms per count modulo 65,536When a prior sample exists, advance 1–32,767 ticks to accept. A repeated tick can indicate that publication continued while acquisition froze.

Relative modular ordering assumes the unseen advance is smaller than half the field range. A long and ambiguous interruption needs an explicit resynchronization policy. Use the source tick to check progression within one generation. Subtracting it from the receiver’s clock would mix different clock origins, and freshly received queued data can still be old. For a source-to-use age requirement, measure or bound acquisition, queueing, link and scheduling delay as well.

Run the same replay through two paths

Download can_freshness.py. The deterministic replay uses Python 3.10 or newer and needs no CAN interface. It exercises exact programmed times and shows how the receiver’s decoding and freshness logic work.

python3 can_freshness.py replay > replay.csv

For the measured run, use only a disposable Linux VM or an isolated test host you administer with Python, ip and can-utils. Create the virtual interface if you have not already set it up in P49. If the running kernel lacks vcan, use its matching optional modules package or stay with replay mode. Linux SocketCAN and the virtual CAN driver.

sudo modprobe vcan
sudo ip link add dev vcan0 type vcan
sudo ip link set vcan0 up

Run the monitor in one terminal. Its timestamps below are deltas between successive frames. Use a separate terminal for the sender and receive logic. Keep other senders off this training interface.

candump -t d -n 14 vcan0
python3 can_freshness.py vcan > measured.csv

The second command uses separate SocketCAN send and receive sockets and checks the received bytes before feeding the monitor. The recorded decisions carry monotonic time since the script started. This virtual link exercises Python and Linux CAN handling. Physical wiring, bus arbitration delays, EMC and firmware timing need a hardware bench. Remove the virtual interface with sudo ip link del dev vcan0 if you created it solely for these exercises.

Make the edge cases observable

  1. Add an invalid frame one millisecond before timeout. Confirm it cannot postpone expiry. Compare with a new valid reading before the deadline.
  2. Make the first valid recovery sample arrive exactly on the deadline in deterministic replay. Keep the expiry record and the recovery record so both decisions are visible.
  3. For a production monitoring plan, specify the receiver’s maximum check interval, a clock and queue-latency budget and how a known session is exchanged. Decide how a display handles stale readings and what a separate controller is allowed to do when evidence expires.

The generation, counter and timer are application checks in a software monitor. Freshness recovery reports data health. Motion authorization and independent stop functions have their own interfaces and acceptance tests.
