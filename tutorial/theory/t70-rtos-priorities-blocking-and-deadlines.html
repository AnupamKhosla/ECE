Task priority, blocking and control deadlines

A control task can miss its deadline even when the arithmetic in the task takes a fraction of the available time. Trace who owns the resource it needs, which other tasks are runnable, and how much time remains after it becomes ready.

Time 35 minBefore this T30 · Firmware timing and recovery · T31 · Feedback control

Follow the task that can make progress

On the single-core scheduler in this exercise, a ready task with higher priority preempts a lower-priority task. A task blocked on a queue, lock or timeout cannot run even when it has the highest task priority. An interrupt can delay dispatch as well. Measure a deadline from the relevant event through scheduling, computation and output, then add actuator response if it belongs in the requirement.

See the inversion in three tasks

  1. A low-priority logger holds a shared record buffer when a high-priority control update arrives.
  2. The control task blocks on the owner. A medium-priority analysis task remains runnable. With a binary semaphore for the shared buffer, it runs ahead of the logger and delays the control task indirectly.
  3. With a FreeRTOS mutex in this single-lock example, the owner inherits the waiting control task’s priority. The logger can finish its critical section, release the buffer and let control run. The analysis task still gets its CPU time afterward.

A binary semaphore suits event signalling. A mutex expresses ownership and gives FreeRTOS a way to inherit priority across the wait. Hold it for the bounded data copy, release it, then format logs or perform storage and network I/O. Inheritance still leaves the control task waiting for the owner to finish. FreeRTOS uses a simplified inheritance scheme, so retest when an owner holds several locks. Use ISR-safe signalling APIs for interrupt-to-task events and check each API’s constraints. Calculate a small response-time budget

Suppose control takes at most 4 ms of CPU and can be blocked for up to 8 ms by one lower-priority resource owner. A higher-priority task needs 3 ms every 10 ms. Use independent periodic higher-priority work, fixed-priority preemptive scheduling and measured or analysed upper bounds as assumptions. There is no extra jitter, blocking chain, interrupt workload or self-suspension in this model.

Start with control execution plus blocking, R₀ = 4 + 8 = 12 ms. Up to two releases of the higher-priority task fit into that interval. The next result is R₁ = 4 + 8 + ceil(12/10) × 3 = 18 ms. Repeating with 18 ms gives the same answer. Under the assumptions, a 20 ms deadline fits. If blocking grows to 12 ms, the sequence becomes 16, 22 and 25 ms. It crosses the deadline even though control still takes 4 ms. Include dispatch, interrupts, release jitter and other resources when analysing a target that has them.

Decide what a late task may do

Give the controller a bounded wait, count missed releases and define what happens to output and data freshness when the budget expires. A deadline miss may require holding a defined output, degrading the mode or requesting a stop through designed interfaces. Test the response with delayed work, missed samples and clustered interrupts. Hardware watchdogs and independent safeguards address different failure modes.

Why can a fast idle-bench loop still miss updates during logging?

CPU timing for the control calculation omits blocking. A logger may hold a buffer, and unblocked medium-priority work can extend the wait. Record the delay from the control release to actual acquisition under simultaneous workloads.
