Talking to devices: UART, I²C, SPI, RS-485 and Modbus

Learn the four wiring "languages" that chips and field devices use to exchange data: UART, I²C and SPI inside gadgets, and RS-485 with Modbus inside every building plant room. By the end you will read a real Modbus device from your laptop, decode a Modbus frame byte by byte, and know the faults that cost BMS technicians hours on site.

The big picture: four ways to send bits

All these buses send bits as HIGH and LOW voltages over time. They differ in how many wires they use, how the receiver knows when to read each bit, how far they go, and how many devices can share the wires.

Common misconception

"RS-485 and Modbus are the same thing." No. RS-485 is only the electrical layer: how voltages on two wires represent 1s and 0s. Modbus RTU is a protocol: what the bytes mean. Modbus can also run over TCP/IP on Ethernet, and RS-485 also carries BACnet MS/TP and many proprietary protocols. On site, separate the two questions: "is the wire working?" and "are we speaking the same language?"

UART: the simplest serial link

A UART (universal asynchronous receiver-transmitter) sends one byte at a time on one wire. "Asynchronous" means there is no clock wire. Instead, both ends agree in advance on the baud rate (bits per second), and each byte is wrapped in a frame that tells the receiver when to start counting.

  • When nothing is being sent, the line rests HIGH (idle).
  • A start bit (LOW) says "a byte is coming". The receiver uses its falling edge to start its timer.
  • Then 8 data bits, least significant bit (LSB) first.
  • An optional parity bit for simple error checking.
  • One or two stop bits (HIGH), which return the line to idle.

The common setting "9600 8N1" means 9600 baud, 8 data bits, no parity, 1 stop bit: 10 bits per byte in total.

bit time = 1 / 9600 ≈ 104.2 µs    byte time = 10 × 104.2 µs ≈ 1.04 ms    → about 960 bytes/s The receiver samples each bit near its middle, timing from the start bit's edge. Its clock may be off by a few percent before the sampling point drifts out of the last bit, which is why both ends must use the same baud rate.

Wiring: TX goes to RX

Each device transmits on its TX pin and listens on its RX pin. So you cross them: TX of one to RX of the other, and the other way round. And you must connect GND, because each receiver judges HIGH and LOW against its own ground (P13).

The Uno's hardware UART (D0/D1) is already used by USB, so for a second port we use the SoftwareSerial library on any two pins. Load the sender on board A and the receiver on board B, wire as Figure 2, and open B's Serial Monitor.

// Board A: sender
#include <SoftwareSerial.h>
SoftwareSerial link(10, 11);          // RX = D10, TX = D11 (a second UART made in software)

void setup() {
  link.begin(9600);                   // both boards MUST use the same baud rate
}

void loop() {
  link.println("Hello from board A"); // sent out of D11 as UART frames, then CR + LF
  delay(1000);
}
// Board B: receiver
#include <SoftwareSerial.h>
SoftwareSerial link(10, 11);          // RX = D10, TX = D11

void setup() {
  Serial.begin(9600);                 // USB serial to the PC's Serial Monitor
  link.begin(9600);                   // the link to board A
}

void loop() {
  while (link.available() > 0) {     // any bytes waiting in the receive buffer?
    char c = link.read();             // take one byte out of the buffer
    Serial.write(c);                  // pass it straight to the Serial Monitor
  }
}
Safety: TTL is not RS-232

Arduino UART pins are "TTL level": 0 V and 5 V (or 3.3 V on 3.3 V boards). The old RS-232 serial port (9-pin D connector on older PCs and some plant equipment) uses roughly ±5 to ±12 V and inverted logic. Connecting RS-232 straight to an Arduino or ESP32 pin can destroy it. Use an RS-232-to-TTL converter module. Also, a 5 V Uno TX into a 3.3 V board's RX needs a divider or level shifter (P11).

I²C: many chips on two wires

I²C (say "I-squared-C", also written I2C) connects many chips on the same board with just two wires: SDA (data) and SCL (clock). One device, the controller (traditionally called master), drives the clock and starts every conversation. Every other device, a target (traditionally called slave), has a 7-bit address, so up to about 112 usable addresses share the bus.

The clever part is electrical. No device ever drives a line HIGH. Each device can only pull a line LOW (an "open-drain" output: a transistor to ground) or let go. Pull-up resistors, typically 4.7 kΩ, pull each line HIGH when nobody is pulling it low. So two devices can never fight (one HIGH, one LOW = short circuit), and any device can hold the clock low to say "wait". This is the same pull-up idea as your button in P11.

A transaction looks like this: the controller sends a START (SDA falls while SCL is high), then the 7-bit address plus a read/write bit. The device with that address answers with an ACK (it pulls SDA low for one clock). Then data bytes follow, each acknowledged, and finally a STOP. If nobody answers, the controller sees a NACK, which is how the scanner below finds devices.

The I²C scanner

Wire your module: VCC to 5 V (or 3.3 V if the module requires it), GND to GND, SDA to A4, SCL to A5. Upload this and open the Serial Monitor. It is the first thing to run with any new I²C part.

#include <Wire.h>                         // built-in I2C library

void setup() {
  Wire.begin();                             // join the bus as controller (Uno: A4 = SDA, A5 = SCL)
  Serial.begin(9600);
  Serial.println("Scanning I2C bus...");
  int found = 0;
  for (byte addr = 1; addr < 127; addr++) { // try every 7-bit address
    Wire.beginTransmission(addr);           // queue START + address + write bit
    byte err = Wire.endTransmission();      // send it, then STOP; returns 0 if a device ACKed
    if (err == 0) {
      Serial.print("Device found at 0x");
      if (addr < 16) Serial.print("0");     // print a leading zero, e.g. 0x0A
      Serial.println(addr, HEX);
      found++;
    }
  }
  Serial.print(found);
  Serial.println(" device(s) found");
}

void loop() {}                              // nothing to repeat
Bench tip

If the scanner hangs or finds nothing: check SDA/SCL are not swapped, the module has power, and pull-ups exist (measure SDA and SCL to GND at idle: both should read the supply voltage). If it finds a device at an unexpected address, many modules have solder jumpers or an address pin that changes it.

SPI: fast, simple, more wires

SPI (serial peripheral interface) uses four wires: SCK (clock, from the controller), MOSI (controller out, peripheral in; also called COPI), MISO (controller in, peripheral out; also called CIPO), and one CS (chip select, also called SS) per device. CS is active LOW: the controller pulls one device's CS low to talk to it, and the others ignore the bus. Data goes both ways at once, one bit in each direction per clock. Lines are actively driven both HIGH and LOW (no pull-ups), so SPI can run at many megahertz.

SPI devices also differ in mode: whether the clock idles low or high (CPOL) and which clock edge samples the data (CPHA). The library sets this from the device's datasheet; if a device returns garbage, the mode or clock speed is the usual suspect. You will mostly use SPI through ready-made libraries (SD cards, displays), so the skill to keep is the wiring and the CS rule.

RS-485: the field bus physical layer

UART, I²C and SPI are fine inside a box. In a building, a controller in the plant room may need to talk to an energy meter 300 m away, through cable trays full of motor cables. A 0/5 V signal would be swamped by noise and lose its shape. RS-485 solves this with a differential pair.

Differential signalling

RS-485 sends each bit on two wires, A and B, twisted together. For one logic state the driver makes A higher than B; for the other, B higher than A. The receiver ignores the voltage of each wire relative to ground and looks only at the difference A − B. A difference of more than +200 mV means one state, less than −200 mV means the other. Because the two wires are twisted together, any interference couples into both equally and the difference does not change. This is called common-mode rejection.

Why it works

The receiver tolerates a common-mode voltage (both wires moving together relative to its ground) of roughly −7 V to +12 V. That covers noise and ground-potential differences between buildings or switchboards, but only if there is a reference connection keeping the devices within that window, which is why a signal common wire is recommended. Twisting matters because a magnetic field induces equal and opposite voltages in neighbouring twists, which cancel.

The rules of an RS-485 bus

  1. Daisy chain, not star. At fast edges the cable behaves as a transmission line. Every branch and every open end reflects part of the signal back, like an echo. A star of long branches creates many echoes that corrupt bits.
  2. Terminate both ends with 120 Ω. Twisted pair has a characteristic impedance of roughly 100–120 Ω. A resistor that matches it at the end absorbs the signal instead of reflecting it. Exactly two terminators per segment, at the two physical ends.
  3. Bias the idle line once. When no device is transmitting, all drivers are off and the line floats, just like a floating input (P11). Bias resistors (often 560 Ω–1 kΩ, one pulling A up and one pulling B down) hold the difference above 200 mV so receivers see a steady idle state. Many adapters and controllers have switchable bias; enable it in one place.
  4. Use proper cable and a common. Shielded twisted pair rated for RS-485 (about 120 Ω). Use a second conductor or pair for the 0 V signal common. Earth the shield at one end only, to avoid a ground loop through the shield.
  5. Load and length limits. The standard allows 32 "unit loads" per segment; many modern transceivers are 1/4 or 1/8 unit load, allowing more devices. Up to about 1200 m at ≤100 kbit/s. A rough rule: length (m) × bit rate (bit/s) ≤ 108. Longer or bigger networks need repeaters.
  6. A and B labels are not standard across brands. Some makers call the non-inverting line A, others B, and some use + and −, D+ and D−. If a correctly addressed device never answers, swap A and B: it does no damage.
Bias check: Vidle = 5 V × 60 Ω / (680 + 60 + 680) Ω ≈ 0.21 V With two 120 Ω terminators (60 Ω in parallel) and 680 Ω bias resistors on 5 V, the idle difference is only 211 mV, just above the 200 mV threshold. That is why bias values are chosen together with termination, and why adding a third terminator (40 Ω total) would drop the idle level to about 0.14 V and cause random errors.
Bench tip

A fast termination check: with every device powered off, measure resistance between A and B at any point on the bus. About 60 Ω means two terminators (correct). About 120 Ω means one is missing. About 40 Ω means three. A much higher reading means none (or bias resistors only).

Modbus RTU: the language

Modbus was created in 1979 for PLCs, and it is still the most common "lowest common denominator" protocol in buildings and industry. It is simple: one master (the Modbus specification now says client) asks questions; slaves (now servers) only answer when asked. Each slave on an RS-485 segment has a unique address from 1 to 247. Address 0 is broadcast (writes only, nobody replies).

Common misconception: the 40001 numbering

"Register 40001" is not an address that goes on the wire. The leading 4 says "holding register table" (so use function 03), and the rest is a 1-based register number. The address actually sent is 0-based: 40001 → address 0; 40108 → address 107 (0x006B); 30001 → input register address 0 with function 04. Some manuals list the 1-based numbers, some list 0-based addresses, some list hex. If every value you read seems to belong to the neighbouring register, you have an off-by-one error. Test by reading one register whose value you can predict.

Serial settings and timing

Every device on one segment must use the same baud rate and framing. The Modbus specification's default is 9600 baud, 8 data bits, even parity, 1 stop bit (8E1), but many devices ship as 8N1, so read the manual. Most devices let you change address, baud and parity from a front panel, DIP switches or software. After sending a request, the master waits for a reply (a timeout of 0.5–1 s is common), then moves on to the next device. Polling 20 devices × 5 requests each at 9600 baud takes a few seconds per cycle, which is why BMS integrators group registers into as few requests as possible.

Modbus TCP

Modbus TCP carries the same function codes and data inside TCP/IP packets on Ethernet, on TCP port 502. The RTU address byte becomes the Unit ID, and the CRC is dropped because Ethernet and TCP already check for errors. The same request as above in Modbus TCP is:

00 01  00 00  00 06  01  04 00 00 00 02 Transaction ID 1 (the client's tag to match the reply), protocol 0, length 6 (bytes that follow), unit ID 1, then the familiar 04 00 00 00 02.

A Modbus gateway converts between the two: it has an IP address on the building network and an RS-485 port to a string of RTU devices. The unit ID in each TCP request tells the gateway which RTU slave address to ask. "Gateway reachable but every device times out" usually means the RS-485 side is wrong, not the network.

Lab: read a Modbus sensor from your laptop

Use a cheap RS-485 Modbus temperature/humidity module. Each make differs, so your module's register list is the authority. A common example layout is: slave address 1, 9600 8N1, input register 1 = temperature × 10, input register 2 = humidity × 10.

  1. Wire it. Module V+ and V− to a 12 V (or 24 V) DC plug-pack, within the module's rated range. Module A to the adapter's A (or D+ / 485+), B to B (or D− / 485−). Use a twisted pair from your Cat6 offcut. For a 1–2 m bench cable, termination is optional; fit 120 Ω across A–B at each end to practise the habit.

  2. Find the port. Plug the USB adapter in. Windows: Device Manager › Ports (COM5, say). macOS: ls /dev/cu.*. Linux: ls /dev/ttyUSB*.

  3. Read it with QModMaster (free, Windows). Set Modbus Mode = RTU. In the RTU options: your COM port, 9600 baud, 8 data bits, no parity, 1 stop bit. Then Slave Addr = 1, Function = Read Input Registers (0x04), Start Address = 1, Number of Registers = 2. Connect, then Read. Check whether your tool's start address is 0-based or 1-based: if values seem shifted by one register, change it by one.

  4. Interpret. Values like 235 and 600 mean 23.5 °C and 60.0 %RH. Breathe on the sensor and read again: both should rise.

  5. Read it with Python. Install the library once with pip install minimalmodbus (it brings pyserial with it), then run the script below.

# read_sensor.py: read a Modbus RTU temperature/humidity module
import minimalmodbus
import serial

PORT = "/dev/ttyUSB0"                  # Windows: "COM5"; macOS: "/dev/cu.usbserial-XXXX"

inst = minimalmodbus.Instrument(PORT, 1)    # port, slave address 1
inst.mode = minimalmodbus.MODE_RTU     # binary RTU framing with CRC
inst.serial.baudrate = 9600            # must match the device
inst.serial.bytesize = 8
inst.serial.parity = serial.PARITY_NONE
inst.serial.stopbits = 1
inst.serial.timeout = 0.5              # seconds to wait for a reply
inst.debug = False                     # set True to print every byte sent and received

# Function 04 = input registers. Address 1 here is the 0-based address on the wire.
temp = inst.read_register(1, number_of_decimals=1, functioncode=4, signed=True)
hum = inst.read_register(2, number_of_decimals=1, functioncode=4)
print(f"Temperature {temp:.1f} C, humidity {hum:.1f} %RH")

number_of_decimals=1 divides the raw value by 10 for you. signed=True treats the register as a signed 16-bit number, so a raw value of 0xFF38 (65 336) becomes −200, that is −20.0 °C. Forget signed and a freezer reads 6533.6 °C.

Bench tip

On Linux and macOS, the free command-line tool mbpoll is handy for quick checks. For example mbpoll -m rtu -a 1 -b 9600 -P none -t 3 -r 2 -c 2 /dev/ttyUSB0 reads two input registers (type 3) starting at reference 2. By default mbpoll uses 1-based references, so reference 2 is address 1. Run mbpoll -h to confirm the options on your version.

Reading a Modbus TCP device

For a device or gateway on Ethernet, pymodbus is a popular library (pip install pymodbus). Its function arguments have changed between versions; the script below is for version 3.x, and the comment shows the newer keyword.

# read_tcp.py: read two holding registers over Modbus TCP
from pymodbus.client import ModbusTcpClient

client = ModbusTcpClient("192.168.1.50", port=502)   # example IP of the device or gateway
if not client.connect():                            # opens the TCP connection
    raise SystemExit("Cannot connect: check IP, cable, and that port 502 is open")

# address=0 means register 40001. In recent pymodbus versions 'slave=' is named 'device_id='.
rr = client.read_holding_registers(address=0, count=2, slave=1)
if rr.isError():
    print("Modbus error:", rr)                      # e.g. an exception response
else:
    print("Raw registers:", [hex(r) for r in rr.registers])
client.close()

32-bit floats and the word-order trap

A Modbus register holds 16 bits. Values like 230.5 V or 123 456 kWh do not fit, so devices put a 32-bit number across two consecutive registers. The Modbus standard does not say which register holds the high half. Some devices send the high word first, some the low word first, and a few also swap the bytes within each word. Your software must use the same order as the device, or you get nonsense.

Order nameRegisters receivedDecoded value
ABCD (big-endian, high word first)0x4366, 0x8000230.5 (correct for this device)
CDAB (word-swapped)read as 0x8000, 0x4366−2.4 × 10−41 (nonsense)
BADC (byte-swapped)0x6643, 0x00802.3 × 1023 (nonsense)
DCBA (little-endian)0x0080, 0x66431.2 × 10−38 (nonsense)

The tell-tale sign: values that are absurdly tiny or huge, or that jump wildly while the real quantity changes slowly. Try the four orders until one gives a sensible number, then confirm against the device's own display.

# decode_float.py: try both word orders on two raw registers
import struct

regs = [0x4366, 0x8000]                 # e.g. from inst.read_registers(0, 2, functioncode=4)

abcd = struct.pack(">HH", regs[0], regs[1])   # first register = high word
cdab = struct.pack(">HH", regs[1], regs[0])   # first register = low word
print("ABCD:", struct.unpack(">f", abcd)[0])  # '>f' = big-endian 32-bit float -> 230.5
print("CDAB:", struct.unpack(">f", cdab)[0])  # nonsense for this device

minimalmodbus can also do it in one call: inst.read_float(0, functioncode=4, byteorder=minimalmodbus.BYTEORDER_BIG), with BYTEORDER_LITTLE_SWAP for the word-swapped (CDAB) order. BMS front ends and gateways have the same setting under names like "swap words", "word order" or "big/little endian".

BACnet MS/TP: the other protocol on RS-485

Many building controllers talk BACnet MS/TP (master-slave/token-passing) on exactly the same RS-485 wiring. The physical rules above are identical: daisy chain, 120 Ω at both ends, bias, shielded twisted pair. The protocol differs: devices pass a "token", and only the holder may transmit, so several masters can share the bus. Each device has a MAC address (0–127 for masters) on the trunk and a separate, network-wide device instance number. Common baud rates are 38 400 and 76 800. Two devices with the same MAC address, or one at the wrong baud rate, can disrupt the whole trunk.

Job Track C02 · BMS protocols and commissioning: BACnet, Modbus, Niagara
On the job

BMS integration is largely this lab, repeated. Chillers, boilers, variable speed drives (VSDs), energy and gas meters, generators and solar inverters expose their data as Modbus registers. You are handed a register map (the manufacturer's table of register numbers, data types and scaling) and a points schedule (what the client wants to see). You set the device's address and comms settings, wire the RS-485 trunk, then create each point in the controller or front end with the right function code, address, data type, word order and scaling, and check the values against the device's own display. Fault-finding tools: a laptop with a USB–RS-485 adapter, QModMaster or Python, a multimeter (termination and bias), and a scope or logic analyser (P15) when it gets hard.

Safety

Energy meters, VSDs and chillers live in switchboards and plant with dangerous voltages. On the bench, practise only with ELV modules like the one in this lab. On site, connect only to the communication terminals provided, follow the site's isolation and permit rules, and leave anything inside a switchboard to a licensed electrician. RS-485 ports on some equipment are not isolated from internal circuits; use an isolated USB–RS-485 adapter when connecting a laptop to plant.

Check yourself

How long does one byte take at 19 200 baud, 8N1?

10 bits (start + 8 data + stop) × 1/19 200 s = 10 × 52.1 µs ≈ 0.52 ms.

Why can two I²C devices never short each other, unlike two push-pull outputs?

I²C outputs are open-drain: they can only pull the line LOW or let go. Only the pull-up resistor makes the line HIGH. If two devices disagree, LOW simply wins through the resistor, and no large current flows.

A manual lists "Frequency: 40017". What function and wire address do you use?

Holding register table, so function 03 to read. Address on the wire = 17 − 1 = 16 (0x0010).

With all devices off, you measure 120 Ω between A and B. What does that tell you?

Only one 120 Ω terminator is fitted (two in parallel would give about 60 Ω). Find the end of the trunk that is missing its terminator.

Why should an RS-485 trunk be a daisy chain and not a star?

At signal edges the cable acts as a transmission line. Branches and unterminated ends reflect energy back as echoes that distort bits. A single line with a matched 120 Ω at each end absorbs the signal at both ends; a star cannot be terminated properly.

A meter's voltage reads −2.4 × 10⁻⁴¹ V. What is wrong?

The two 16-bit halves of the 32-bit float are in the wrong order (word swap). Swap the word order in the software or gateway and the value becomes sensible (230.5 V in our example).

What does a response starting 01 83 02 mean?

Slave 1 is reporting an exception (0x83 = 0x03 + 0x80) to a "read holding registers" request, with exception code 02: illegal data address. The register you asked for does not exist on that device.

Why does Modbus TCP not need the CRC?

Ethernet frames carry their own CRC and TCP has its own checksum and retransmission, so corrupted data is detected and resent by the network layers below Modbus.
