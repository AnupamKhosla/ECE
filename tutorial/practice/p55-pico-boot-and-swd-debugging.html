P55

Find where a Raspberry Pi Pico program stops

The LED stopped blinking after a firmware change. First establish which part of the boot path is working, then pause your own firmware and read the last point it reached.

Time 75–100 minutesBefore this P11 · P14 · P16 · P27
What you’ll use

Original RP2040 Raspberry Pi Pico with onboard LED on GPIO25, known data cable, test-only Pico firmware, the Raspberry Pi Debug Probe or compatible documented CMSIS-DAP probe and the Pico C/C++ SDK toolchain if doing SWD. On other Pico versions, follow their own LED pin and target configuration.

Prove the board before opening the debugger

Verify the test cable transfers data and plug it into a known-good USB port. On the original Pico hold BOOTSEL while plugging in to check the read-only boot facility presents a USB mass storage drive. Release before ordinary reset and prove a known-good LED firmware goes through initialisation. A board in BOOTSEL can still have an application image or runtime fault. Use a spare whose firmware you can replace.

Official probe wiring and tool commands · Pico versions and pinouts.

Compare serial evidence with the paused program state

For a repeatable fault, build this as the application source in a Pico SDK blink project. Enable a serial output through the SDK configuration. Use the same build and ELF file throughout the test. The LED stays lit while the request waits.

#include <stdbool.h>
#include <stdio.h>
#include "pico/stdlib.h"

volatile bool ready = false;

int main(void) {
    stdio_init_all();
    gpio_init(25);
    gpio_set_dir(25, GPIO_OUT);
    gpio_put(25, 1);
    puts("before wait");
    while (!ready) {
        sleep_ms(20);
    }
    puts("after wait");
    gpio_put(25, 0);
    for (;;) {
        sleep_ms(1000);
    }
}

In a second build initialise ready to true. Compare the LEDs and the last message, with the serial viewer open before reset. If using USB stdio, enumeration may take long enough to miss an early one-time message. The probe’s UART path gives an independent check.

  1. Keep a minimal blink firmware and a second debug build of your own. Add a line before and after a wait, and create a deliberate test fault by making the wait condition remain false. If using UART, match voltage, baud and common ground. Observe which log lines appear.
  2. With USB power disconnected, wire SWCLK, ground and SWDIO from the probe according to the official table. The target needs its own appropriate power connection. Keep the debug and UART connectors separate. Use the rp2040.cfg target config for the original Pico.
  3. Run OpenOCD in one terminal using the command below. In another terminal open GDB with the matching ELF file built with debug symbols. Start with the known blink build so you can distinguish a target connection error from a software observation.
openocd -f interface/cmsis-dap.cfg -f target/rp2040.cfg -c "adapter speed 5000"
arm-none-eabi-gdb build/your_app.elf
    (gdb) target extended-remote localhost:3333
    (gdb) monitor reset halt
    (gdb) break main
    (gdb) continue

If you flashed an older build, load your test build first by the documented method and then reset. Step from initialisation or set a breakpoint before the wait. Use bt after halting a running target to read the call stack. Inspect ready with print ready. On this test firmware only, try set variable ready = true and continue. Check that the LED goes out. Rebuild with the correct logic and verify it without the probe. Optimisation can hide variables and reorder apparent stepping.

Record which boundary actually failed

USB enumeration without serial text can mean the program never reached the UART message, the wrong interface is open or the port settings differ. A reachable SWD target with breakpoints stopping at the waiting line supports the firmware hypothesis. A failed probe connection moves the next check to ground, signal wiring, target power and debugger configuration. Check these on the known-good spare before replacing your application board.

Remove the introduced fault and repeat cold startup with the debugger detached. Record the board revision, firmware build, last working log line, where the debugger stopped and a reproducible boot result.
