P162

Recover a robot station journal after interruption

Follow three jobs through a simulated station and inspect which evidence qualifies a good count. Restart the journal process at two transaction boundaries and verify that repeated deliveries preserve the same outcome.

Time 65–85 minutesBefore this P161 · T66

Read the station’s input contract

Download the synthetic station transcript and the Python replay into one writable folder. Use Python 3 with SQLite from its standard library. The files describe an offline exercise. The transcript is in receiver order and the timestamps come from different source clocks.

A PLC registration declares the job key, part serial and recipe. For a good part the journal needs matching camera inspection, independent placement proof and a good robot result in the current evidence generation. The source labels are assigned in the exercise. A deployment would verify those origins at its interface.

Establish the baseline and replay it

Use a new database filename for each experimental run. The report shows exactly which evidence IDs were committed for each serial. Running apply twice against the same file reproduces the station’s event replies from retained history.

python3 journal.py apply baseline.sqlite station-events.csv
python3 journal.py report baseline.sqlite
python3 journal.py apply baseline.sqlite station-events.csv
python3 journal.py report baseline.sqlite

Record the final good count, the held job and the three source events proving each counted part. Find a repeated delivery that received the same stored decision. Compare its ID and payload before and after replay.

Exit the process just before and just after commit

Both cases stop the Python process on fixture-302, the last piece of evidence needed for the first good part. The before-commit case exits after the writes have been staged. The after-commit case exits after the transaction finishes but before a reply appears. Look up the retained count before replaying each transcript, then compare the final reports.

python3 journal.py apply before.sqlite station-events.csv \
  --crash-event fixture-302 --crash-stage before-commit
python3 journal.py report before.sqlite
python3 journal.py apply before.sqlite station-events.csv
python3 journal.py report before.sqlite
python3 journal.py apply after.sqlite station-events.csv \
  --crash-event fixture-302 --crash-stage after-commit
python3 journal.py report after.sqlite
python3 journal.py apply after.sqlite station-events.csv
python3 journal.py report after.sqlite

The injected exits intentionally return nonzero. Run the commands as separate steps so you can inspect the database after each exit. This experiment exercises process failure on a local store. Installed power-loss behavior depends on the chosen persistence design and needs its own validation. SQLite · Synchronization and durability.

Check the two interruption results

The baseline records PART-042 with fixture-302 and PART-043 with robot-204. Job CELL4:8:42 has a new job key but repeats PART-042, so it remains held as a duplicate part. Before commit the report has zero good parts. After commit it has one. Replaying the whole transcript brings both to two. In the after case, the original first-good reply is returned as a replay from the stored event.

Turn the replay into a handover test

Copy the transcript and change the timestamp under an existing event ID while keeping its job and part. Reapply against an existing training database and compare the error and count. Then write four acceptance checks covering a late result, loss before reply, resumed evidence and duplicate physical serial. Include the first human verification of fixture state and who can release that hold. Keep the report JSON as part of the evidence record.
