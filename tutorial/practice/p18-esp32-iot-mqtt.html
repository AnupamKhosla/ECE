ESP32 and IoT: Wi-Fi, MQTT and dashboards

You will program an ESP32 to join Wi-Fi, run an MQTT broker on your Raspberry Pi, make the ESP32 publish temperature and obey an LED command, and watch it all on a dashboard — using the same topic naming, security habits and architecture as building IoT systems.

Time 3–4 hLevel IntermediateKit cost ~A$20–30 on top of P16/P17Theory T10, T15

Safety

The ESP32 is a 3.3 V chip and its pins are not 5 V tolerant, just like the Pi. The board's 5 V (VIN/5V) pin comes from USB: never connect it to a GPIO. Everything here is USB-powered ELV. Do not connect IoT relay boards to mains loads — switching 230 V is licensed electrical work in Australia.

Meet the ESP32

The ESP32 from Espressif is a microcontroller (like the Arduino's chip, P11) with Wi-Fi and Bluetooth built in. It has two processor cores at up to 240 MHz, about 520 kB of RAM, 4 MB of flash on a typical module, and plenty of GPIO. It costs a few dollars, so it is inside a huge number of smart plugs, sensors and gateways.

Arduino IDE setup

  1. Add the board package. In Arduino IDE 2: File → Preferences → "Additional boards manager URLs", add https://espressif.github.io/arduino-esp32/package_esp32_index.json. Then Tools → Board → Boards Manager, search "esp32", install esp32 by Espressif Systems.

  2. Install libraries (Sketch → Include Library → Manage Libraries): PubSubClient by Nick O'Leary, OneWire, and DallasTemperature.

  3. Select the board and port. Tools → Board → esp32 → ESP32 Dev Module; Tools → Port → the new COM port (Windows) or /dev/cu.usbserial-… / /dev/cu.SLAB_USBtoUART (macOS). No port? The board's USB-serial chip (often CP2102 or CH340) may need a driver from the chip maker, or your cable is charge-only.

  4. Upload. If you see "Failed to connect to ESP32: Wrong boot mode detected", hold the BOOT button while "Connecting…" appears, then release.

First sketch: join Wi-Fi

#include <WiFi.h>

const char* WIFI_SSID = "BenchIoT";
const char* WIFI_PASS = "change-me";

void setup() {
  Serial.begin(115200);
  WiFi.mode(WIFI_STA);                 // station = a client of an access point
  WiFi.begin(WIFI_SSID, WIFI_PASS);
  Serial.print("Connecting");
  while (WiFi.status() != WL_CONNECTED) {
    delay(500);
    Serial.print(".");
  }
  Serial.println();
  Serial.print("IP address: "); Serial.println(WiFi.localIP());
  Serial.print("Gateway:    "); Serial.println(WiFi.gatewayIP());
  Serial.print("RSSI:       "); Serial.print(WiFi.RSSI()); Serial.println(" dBm");
}

void loop() {}

Open the Serial Monitor at 115200 baud and press the board's EN (reset) button:

Connecting.....
IP address: 192.168.1.57
Gateway:    192.168.1.1
RSSI:       -58 dBm

RSSI (received signal strength) is in dBm: decibels relative to 1 milliwatt, always negative here. −58 dBm is a solid link. Rule of thumb: better than −67 dBm is reliable; −70 to −80 dBm works but drops out; worse than −80 dBm is trouble. Every 3 dB is a factor of two in power, so −70 dBm is 4 times weaker than −64 dBm.

Why it works

Wi-Fi at 2.4 GHz has a wavelength of about 12.5 cm. The signal weakens with distance (spreading out) and with every wall, floor and metal cabinet it passes through. A plant room with steel switchboards and concrete is a hostile place for Wi-Fi; that is why many building sensors use wired buses or LoRaWAN instead.

Theory T10 · Electromagnetic waves, antennas and optical fibre

MQTT in one picture

MQTT is a small messaging protocol designed for unreliable networks and tiny devices. It runs over TCP, normally on port 1883 (or 8883 with TLS encryption). The key idea is publish/subscribe: devices never talk to each other directly. They all connect to one central server called the broker.

  • A client is anything that connects to the broker: your ESP32, a dashboard, a script.
  • To send data, a client publishes a message to a topic, a text address like bench/l1/plantroom/temp. The message body is called the payload (here, 23.94).
  • To receive data, a client subscribes to a topic or a pattern of topics. The broker forwards every matching message to every subscriber.
  • The publisher does not know or care who is listening. Add a second dashboard tomorrow and nothing on the ESP32 changes.

QoS, retained messages and the last will

QoS (quality of service) is how hard MQTT tries to deliver each message:

  • QoS 0 — at most once. Send and forget. Cheapest. Fine for a temperature sent every 10 s: if one is lost, the next one arrives soon.
  • QoS 1 — at least once. The receiver must reply with PUBACK; the sender repeats until it does. A message may arrive twice. Good for commands ("LED ON" twice does no harm).
  • QoS 2 — exactly once. A four-step handshake. Slowest. For things where a duplicate would hurt (e.g. "add one to a counter").
  • Retained message: the broker keeps the last message published with the "retain" flag on a topic, and hands it to any new subscriber immediately. Without it, a dashboard opened at 9:00 shows nothing until the next reading arrives. Retain states and slow-changing values; do not retain one-off events or commands.
  • Last will and testament (LWT): when a client connects it can leave a "will" with the broker: "if I vanish without saying goodbye, publish offline to …/status". The broker notices the client is gone when its keepalive pings stop (PubSubClient default: 15 s, the broker waits about 1.5 × that). This is how a dashboard shows "device offline" — the IoT version of a BMS comms-fail alarm.

Install the Mosquitto broker on the Pi

sudo apt update
sudo apt install -y mosquitto mosquitto-clients
sudo systemctl enable --now mosquitto
systemctl status mosquitto          # expect: active (running)

Out of the box, Mosquitto 2.x only accepts connections from the Pi itself. That is a safe default. We add a network listener with passwords. Create /etc/mosquitto/conf.d/bench.conf with sudo nano:

listener 1883
allow_anonymous false
password_file /etc/mosquitto/passwd
acl_file /etc/mosquitto/acl

Create one user per client. -c creates a new file, so use it for the first user only — using it again wipes the others.

sudo mosquitto_passwd -c /etc/mosquitto/passwd tech
sudo mosquitto_passwd /etc/mosquitto/passwd esp32-01
sudo mosquitto_passwd /etc/mosquitto/passwd nodered

The ACL (access control list) says which user may read or write which topics. A sensor should only write its own topics; a dashboard should not be able to impersonate a sensor. Create /etc/mosquitto/acl:

# technician: everything under bench/
user tech
topic readwrite bench/#

# dashboard: read all, but only write LED commands
user nodered
topic read bench/#
topic write bench/+/+/led/set

# one ESP32 node: only its own topics
user esp32-01
topic write bench/l1/plantroom/temp
topic write bench/l1/plantroom/temp/fault
topic write bench/l1/plantroom/led/state
topic write bench/l1/plantroom/esp32-01/status
topic read bench/l1/plantroom/led/set
sudo chown root:mosquitto /etc/mosquitto/passwd /etc/mosquitto/acl
sudo chmod 640 /etc/mosquitto/passwd /etc/mosquitto/acl
sudo systemctl restart mosquitto
sudo ss -tlnp | grep 1883          # expect 0.0.0.0:1883 ... mosquitto

Test it with two SSH windows. Window 1 subscribes to everything under bench/ (-v prints the topic too):

tech@plantpi:~ $ mosquitto_sub -h localhost -u tech -P 'your-password' -t 'bench/#' -v

Window 2 publishes:

tech@plantpi:~ $ mosquitto_pub -h localhost -u tech -P 'your-password' -t 'bench/l1/plantroom/temp' -m 22.5

Window 1 prints bench/l1/plantroom/temp 22.5. Try a wrong password: you get Connection error: Connection Refused: not authorised. That refusal is the proof your security works. (Typing a password after -P leaves it in your shell history; on a real site use a config file or a prompt.)

The ESP32 node: publish temperature, obey the LED

Keep passwords out of the main sketch. In the Arduino IDE, add a new tab (the "…" menu → New Tab) called secrets.h:

#pragma once
#define WIFI_SSID  "BenchIoT"
#define WIFI_PASS  "change-me"
#define MQTT_HOST  "192.168.1.42"          // the Pi's IP (more reliable than .local on an ESP32)
#define MQTT_USER  "esp32-01"
#define MQTT_PASS  "a-long-random-password"

The main sketch, plantroom_node.ino:

// ESP32 MQTT node: publishes temperature, obeys an LED command.
#include <WiFi.h>
#include <PubSubClient.h>
#include <OneWire.h>
#include <DallasTemperature.h>
#include "secrets.h"

const int ONE_WIRE_PIN = 4;     // DS18B20 data, 4.7k pull-up to 3V3
const int LED_PIN      = 26;    // LED + 330 ohm to GND

const char* NODE_ID     = "esp32-01";
const char* T_TEMP      = "bench/l1/plantroom/temp";
const char* T_FAULT     = "bench/l1/plantroom/temp/fault";
const char* T_LED_SET   = "bench/l1/plantroom/led/set";
const char* T_LED_STATE = "bench/l1/plantroom/led/state";
const char* T_STATUS    = "bench/l1/plantroom/esp32-01/status";

const unsigned long SAMPLE_MS = 10000;   // publish every 10 s

WiFiClient net;
PubSubClient mqtt(net);
OneWire oneWire(ONE_WIRE_PIN);
DallasTemperature sensors(&oneWire);

unsigned long lastSample = 0;
unsigned long lastTry = 0;
bool ledOn = false;

void setLed(bool on) {
  ledOn = on;
  digitalWrite(LED_PIN, on ? HIGH : LOW);
  mqtt.publish(T_LED_STATE, on ? "ON" : "OFF", true);      // retained state
}

// Called by mqtt.loop() for every message on a subscribed topic.
void onMessage(char* topic, byte* payload, unsigned int length) {
  String msg;
  for (unsigned int i = 0; i < length; i++) msg += (char)payload[i];
  msg.trim();
  Serial.printf("RX %s = %s\n", topic, msg.c_str());
  if (strcmp(topic, T_LED_SET) == 0) {       // compare BEFORE publishing:
    if (msg.equalsIgnoreCase("ON"))  setLed(true);    // publish reuses the buffer
    else if (msg.equalsIgnoreCase("OFF")) setLed(false);
  }
}

void connectWiFi() {
  WiFi.mode(WIFI_STA);
  WiFi.begin(WIFI_SSID, WIFI_PASS);
  Serial.print("WiFi");
  while (WiFi.status() != WL_CONNECTED) { delay(500); Serial.print("."); }
  Serial.printf("\nIP %s  RSSI %d dBm\n",
                WiFi.localIP().toString().c_str(), WiFi.RSSI());
}

bool connectMqtt() {
  // Last will: if we drop off, the broker publishes "offline" (retained, QoS 1).
  if (mqtt.connect(NODE_ID, MQTT_USER, MQTT_PASS, T_STATUS, 1, true, "offline")) {
    mqtt.publish(T_STATUS, "online", true);
    mqtt.subscribe(T_LED_SET, 1);
    mqtt.publish(T_LED_STATE, ledOn ? "ON" : "OFF", true);
    Serial.println("MQTT connected");
    return true;
  }
  Serial.printf("MQTT failed, state=%d\n", mqtt.state());
  return false;
}

void setup() {
  Serial.begin(115200);
  pinMode(LED_PIN, OUTPUT);
  digitalWrite(LED_PIN, LOW);
  sensors.begin();
  connectWiFi();
  mqtt.setServer(MQTT_HOST, 1883);
  mqtt.setCallback(onMessage);
}

void loop() {
  if (WiFi.status() != WL_CONNECTED) connectWiFi();

  if (!mqtt.connected()) {
    if (millis() - lastTry > 5000) {     // retry every 5 s, never hammer the broker
      lastTry = millis();
      connectMqtt();
    }
  } else {
    mqtt.loop();                         // receive messages, send keepalive pings
  }

  if (millis() - lastSample >= SAMPLE_MS) {
    lastSample = millis();
    sensors.requestTemperatures();       // up to 750 ms at 12-bit
    float t = sensors.getTempCByIndex(0);
    bool fault = (t == DEVICE_DISCONNECTED_C) || (t == 85.0f);
    if (mqtt.connected()) {
      mqtt.publish(T_FAULT, fault ? "1" : "0", true);
      if (!fault) {
        char buf[12];
        snprintf(buf, sizeof(buf), "%.2f", t);
        mqtt.publish(T_TEMP, buf, true);
        Serial.printf("TX %s = %s\n", T_TEMP, buf);
      }
    }
  }
}

Things worth noticing:

  • No long delay() in loop(). mqtt.loop() must run often to receive commands and send keepalives. Timing uses millis() (P11).
  • Reconnect logic with a 5 s back-off. Wi-Fi drops, brokers restart. A device that never reconnects is a site visit.
  • Separate command and state topics. The dashboard publishes to led/set; the ESP32 reports what it actually did on led/state. If the two disagree, something is wrong — exactly like a BMS "command vs status" mismatch alarm.
  • Sensor fault is published separately from the value. Never publish the word "fault" on a numeric topic; it breaks every chart.
  • PubSubClient publishes at QoS 0 and can subscribe at QoS 0 or 1. Its default maximum packet size is 256 bytes (mqtt.setBufferSize() raises it) — fine for short payloads.

# subscriber shows:

bench/l1/plantroom/led/state ON

Finally pull the ESP32's USB cable. About 20 s later (keepalive timeout) the subscriber prints bench/l1/plantroom/esp32-01/status offline. That is the last will working.

Topic names: build them like a building

Topics are hierarchical, separated by /, case-sensitive, and free-form. Free-form is dangerous: a year later you have Temp1, plantroom_temp and sensors/PR/t on the same site. Decide a pattern on day one. A pattern that mirrors the building works well:

site / level / room / point [/ sub-point] Example: bench/l1/plantroom/temp, bench/l1/plantroom/led/set. Lower case, no spaces, no leading slash, nouns not sentences.

Wildcards are only for subscribing (never in a published topic):

  • + matches exactly one level: bench/+/+/temp = every room temperature on every level.
  • # matches any number of levels, including zero, and must be last: bench/l1/# = everything on level 1 (and bench/l1 itself).
  • Topics starting with $ (such as the broker's own $SYS/… statistics) are not matched by a filter that starts with a wildcard.

A dashboard with Node-RED

Node-RED is a free, browser-based tool where you wire "nodes" together into flows: an MQTT input node feeds a gauge node, a switch node feeds an MQTT output node. It is widely used for quick IoT dashboards and protocol glue (Modbus, BACnet and MQTT nodes all exist).

  1. Install. Use the official Raspberry Pi install script from the Node-RED website (nodered.org → Docs → Getting Started → Raspberry Pi). It is one command that installs Node.js and Node-RED and asks a few setup questions — say yes to setting up a login (user security). Then sudo systemctl enable --now nodered.service.

  2. Open the editor at http://plantpi.local:1880. Menu (☰) → Manage palette → Install → search @flowfuse/node-red-dashboard (Dashboard 2.0) → install.

  3. Temperature in. Drag an mqtt in node. Add a new broker: server localhost, port 1883, Security tab: user nodered and its password. Topic bench/+/+/temp, QoS 0, output "auto-detect". Wire it to a gauge (range 0–40, units °C) and a chart (line, 1 hour). Dashboard nodes need a group/page: accept the defaults it offers.

  4. Status. Another mqtt in on bench/+/+/+/status → a text widget labelled "Node". It shows online / offline from the last will.

  5. Command out. A switch widget with "on payload" string ON and "off payload" string OFF → an mqtt out node, topic bench/l1/plantroom/led/set, QoS 1, retain false.

  6. Deploy (top right), then open http://plantpi.local:1880/dashboard on your phone. Flick the switch: the LED follows within a fraction of a second.

Bench tip

Never retain a command topic. If led/set ON is retained, the ESP32 receives "ON" again every time it reconnects — perhaps hours after someone turned it off from somewhere else. Retain states, not commands.

Home Assistant is the other popular choice, aimed at homes. It has an MQTT integration that can talk to the same Mosquitto broker, and supports "MQTT discovery", where a device publishes a small JSON description of itself so it appears automatically. Either tool is fine for learning; the MQTT side does not change.

Bonus: your P17 Flask logger can be made an MQTT publisher too, with the paho-mqtt Python library (sudo apt install python3-paho-mqtt). Then the Pi's own sensor and the ESP32's appear side by side on the same dashboard.

Security basics (do not skip)

IoT devices are a favourite way into networks because they are installed once and forgotten. The basics stop almost all of it:

  • No anonymous access, and one username and password per device, with an ACL that limits each device to its own topics. A stolen sensor then exposes one sensor, not the site.
  • Never expose the broker to the internet. No port-forward of 1883 on the router, ever. Internet scanners find open MQTT brokers within hours and read (or write) everything. Need remote access? Use a VPN into the site, or a properly secured cloud broker with TLS.
  • Put IoT on its own network: a separate SSID and VLAN (P19) with firewall rules, so a compromised sensor cannot reach the office PCs, cameras or the BMS.
  • Use TLS (port 8883) whenever traffic leaves a trusted network, so passwords and data are encrypted in transit. Plain 1883 sends passwords in clear text.
  • Keep secrets out of code repositories. The secrets.h file never goes into Git or a forum post. Change default passwords on every device.
  • Patch: update the Pi (apt full-upgrade), Mosquitto, Node-RED and the ESP32 firmware on a schedule.
Common misconception

"It's only a temperature sensor, nobody cares." Attackers do not want your temperature. They want a foothold on the network: a device with an IP address, network access and no monitoring. From there they reach the things that matter. Treat every IoT device as a computer on your network, because it is one.

In Australia · LoRaWAN for long-range sensors

Wi-Fi reaches tens of metres. For sensors spread across a campus, a farm or a whole building, LoRaWAN is common: battery sensors send a few bytes every few minutes over sub-GHz radio, reaching kilometres in open country (much less in dense buildings — indicative only), and batteries can last years. Sensors talk to gateways, gateways forward to a network server, and the network server usually hands data on via — you guessed it — MQTT. In Australia buy devices for the AU915 frequency plan (915–928 MHz), which operates under the ACMA's class licence for low-interference devices; community networks such as The Things Network use AU915 sub-band 2. Check the current ACMA rules and your network provider's settings before deploying. You will see LoRaWAN in smart-building (occupancy, air quality, water leaks) and agriculture (soil moisture, tank levels) jobs.

On the job

Building IoT projects — wireless sensors for air quality and occupancy, energy meters, lift and tank monitoring — are increasingly common next to the traditional BMS. The jobs need people who can commission a device onto Wi-Fi or LoRaWAN, confirm data reaches the broker with mosquitto_sub, name points consistently, and keep the devices off the corporate network. Integrators also bridge MQTT to BACnet or Modbus so IoT data appears on the BMS front end. See C01 and C02.

Check yourself

A dashboard opened at 9:00 shows nothing until 9:00:10. What MQTT feature fixes that, and on which topics?

Retained messages. Publish the temperature, LED state and status with retain = true, so the broker hands the last value to any new subscriber immediately. Do not retain commands such as led/set.

Which QoS would you choose for (a) temperature every 10 s, (b) "unlock door 3", and why?

(a) QoS 0: a lost sample is replaced 10 s later. (b) At least QoS 1, so it is acknowledged and retried. Unlock is safe to repeat (idempotent), so QoS 1 is enough; real access control systems add their own confirmation (status topic) on top.

Does bench/+/temp match bench/l1/plantroom/temp?

No. + matches exactly one level, so the filter has 3 levels and the topic has 4. Use bench/+/+/temp or bench/#.

How does the dashboard learn that the ESP32 has died without saying goodbye?

The ESP32 registered a last will (…/status = offline, retained) when it connected. When its keepalive pings stop, the broker times it out and publishes the will on its behalf. The dashboard is subscribed to the status topic.

A client tells you to port-forward 1883 so they can see the dashboard from home. What do you say?

No: an internet-facing plain MQTT port will be found and abused quickly, and it sends passwords in clear text. Offer a VPN into the site, or a properly secured cloud service with TLS and per-device credentials.

Why publish the LED state separately from the LED command?

The command is what someone asked for; the state is what the device actually did. A mismatch reveals a fault (device offline, relay stuck, ACL blocking). BMS systems do the same with command and status points (e.g. fan start command vs fan run status).

RSSI changes from −55 dBm to −73 dBm when the ESP32 goes into a metal cabinet. How much weaker is the signal?

18 dB weaker. Every 10 dB is ×10 and every 3 dB about ×2: 18 dB ≈ 10 × 100.8 ≈ 63 times less power. That is why metal cabinets need an external antenna or a wired connection.

Your ESP32 is on Wi-Fi but gets state=-2. The Pi is on Ethernet. Name the first check.

Are they on the same network? Compare the ESP32's IP (Serial Monitor) with the Pi's (ip a). A guest SSID or an IoT VLAN may block traffic to the Pi. Then confirm the broker listens on 0.0.0.0:1883, not only localhost.
